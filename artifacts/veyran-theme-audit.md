# VeyraN Light/Dark/System — theme architecture & migration audit

Branch `agent/claude-theme`, worktree `/Users/ozel0t/Notesnook/agents/claude-theme`.
This documents the theme system as it exists before this change, the migration
risk it implies, and the design decisions used to add first-class VeyraN
Light/Dark + System appearance on top of it.

## 1. Shared engine (`@notesnook/theme`, `packages/theme`)

- `ThemeDefinition` (`packages/theme/src/theme-engine/types.ts`) is the schema
  every theme (built-in or user-installed/custom) must satisfy: `id`,
  `colorScheme: "light"|"dark"`, a fully-specified `scopes.base` (6 variants ×
  11 colors), and optional partial overrides for 10 other scopes (`statusBar`,
  `list`, `editor`, `editorToolbar`, `editorSidebar`, `titleBar`, `dialog`,
  `navigationMenu`, `contextMenu`, `sheet`). Missing colors fall back through
  `scopes.base` → the bundled default theme's matching scope → the bundled
  default theme's `base` (`theme-engine/utils.ts:buildVariants`).
- `useThemeEngineStore` (`theme-engine/index.ts`) is a single zustand store
  holding **one** `ThemeDefinition` at a time (`theme`, `setTheme`). It has no
  concept of "light theme" + "dark theme" + "which one is active" — that
  concept lives entirely in each app's own store. The engine is a pure sink:
  whatever `ThemeDefinition` is pushed into it is what every
  `useThemeColors()`/`EmotionThemeProvider` consumer renders.
- `themeToCSS()` emits `.theme-scope-<scope>` / `.theme-scope-<scope>-<variant>`
  blocks of CSS custom properties, named `--<color>` for the `primary` variant
  and `--<color>-<variant>` otherwise (e.g. `--background`,
  `--background-secondary`, `--accent-error`). Consumed on web/desktop via a
  `<style id="theme-colors">` injected by `apps/web/src/index.ts` (pre-hydration,
  flash-of-unstyled-content guard) and re-generated by
  `apps/web/src/components/theme-provider/index.tsx`.
- `validateTheme()` (`theme-engine/validator.ts`) enforces the hex-color regexes
  and required-key list above; used when a user imports a custom theme file.
- The two bundled defaults (`default-light` / `default-dark`, confirmed ids)
  are fetched from the external `streetwriters/notesnook-themes` GitHub repo at
  build time (`packages/theme/scripts/prebuild.mjs`) into
  `packages/theme/src/theme-engine/themes/*.json`, a **gitignored** directory
  (`packages/theme/.gitignore: **/themes/`). They are not checked into this
  repo; I fetched them locally (also gitignored, same directory) purely as
  ground truth to confirm their real `id` strings and palette shape while
  designing VeyraN's palette and the migration key.

## 2. Per-app "which theme is active" stores

### Web / Desktop (Electron renders the same web bundle)

- `apps/web/src/stores/theme-store.ts` owns `lightTheme`, `darkTheme`,
  `colorScheme: "light"|"dark"`, and **`followSystemTheme: boolean`** — System
  appearance already exists here and already live-updates via
  `apps/web/src/hooks/use-system-theme.ts` (`matchMedia("(prefers-color-scheme:
  dark)")` with a live change listener, plus an Electron-only tRPC subscription
  to the main process's `nativeTheme.on("updated")`).
- Persistence is flat `localStorage` keys via `apps/web/src/utils/config.ts`:
  `colorScheme` (default `"light"`), `theme:light` / `theme:dark` (default =
  bundled `ThemeLight`/`ThemeDark`), `followSystemTheme` (default `false`).
  These survive logout (`Config`'s `logout()` explicitly preserves them) —
  theme choice is a local-device preference, not account-synced.
- Electron main process independently tracks its own `config.theme:
  "system"|"light"|"dark"` (`apps/desktop/src/utils/theme.ts`,
  `apps/desktop/src/utils/config.ts`) purely for window chrome (`nativeTheme
  .themeSource`, `BrowserWindow.backgroundColor`, `vibrancy`,
  `titleBarOverlay.symbolColor`). The renderer pushes to it via
  `desktop.integration.changeTheme.mutate(...)` — any change to which
  theme/scheme is "current" must go through the *existing* `theme-store.ts`
  setters (`setTheme`/`setColorScheme`/`setFollowSystemTheme`) so this stays
  in sync; this migration does not bypass those setters.
- UI: `apps/web/src/dialogs/settings/appearance-settings.ts` has a
  light/dark/**auto** dropdown (already the System toggle) plus
  `ThemesSelector` for picking any installed/custom theme from the theme
  marketplace (`themes-api.notesnook.com`, gated by
  `THEME_COMPATIBILITY_VERSION`).

**Migration signal available on web:** `theme-store.ts`'s `isThemeCurrentlyApplied(id)`
compares against `lightTheme.id`/`darkTheme.id`. Since the confirmed bundled
ids are `default-light`/`default-dark`, the safe migration predicate is:
`lightTheme.id === "default-light" && darkTheme.id === "default-dark"` (i.e.
still on the shipped default theme content, whether or not the user ever
opened Settings) → replace with VeyraN equivalents, **preserving** whatever
`colorScheme`/`followSystemTheme` they already have. Any other `id` (a
different installed theme, or a hand-edited custom theme) is left untouched.
No separate "explicit vs. default" flag is persisted anywhere in this store —
the theme `id` itself is the only reliable, stable signal; `colorScheme`
alone is not usable as a signal because `followSystemTheme`'s own live-update
effect writes `colorScheme` on every OS-scheme change, so its presence in
localStorage does not imply an explicit user choice.

### Monograph

No theme preference, no persistence, hardcoded to `ThemeDark`
(`apps/monograph/app/root.tsx`). Out of scope — nothing to migrate, nothing to
default to System.

### Mobile (iOS/iPadOS + Android)

- `apps/mobile/app/stores/use-setting-store.ts` — `defaultSettings` already
  ships `useSystemTheme: true`, so **new mobile installs already default to
  System appearance**; no change needed there. It also ships
  `colorScheme: "light"`, `lighTheme: ThemeLight` (sic, existing typo — not
  renamed, out of scope), `darkTheme: ThemeDark`.
- `apps/mobile/app/services/settings.ts` is the persistence layer: a single
  MMKV key `"appSettings"` holding the whole settings blob, loaded in `init()`.
  Fresh install (`!settingsJson`) → the in-memory `defaultSettings` object is
  used verbatim and persisted. Existing install → the persisted blob is
  spread over the in-memory defaults (`{...settings, ...settingsParsed}`), so
  persisted `lighTheme`/`darkTheme`/`colorScheme`/`useSystemTheme` always win
  over new code defaults — i.e. **just changing `defaultSettings` does not
  by itself touch any existing user**, exactly the "preserve explicit/custom"
  requirement, but it also means old-default users need an explicit migration
  step to ever see VeyraN.
- `migrateSettings()` already exists and runs once per version bump, gated on
  `settings.settingsVersion` — this is the existing, idiomatic place to add a
  one-time "if still on the shipped default theme, swap to VeyraN" migration
  (see §3).
- `apps/mobile/app/stores/use-theme-store.ts` mirrors the web store's shape
  (`lightTheme`, `darkTheme`, `colorScheme`, no separate `followSystemTheme`
  flag — instead `useSystemTheme` lives directly in the settings store) and is
  kept in sync with `useThemeEngineStore` in `apps/mobile/app/app.tsx`
  (`withTheme` HOC), including a live `Appearance.addChangeListener` that only
  reacts when `useSystemTheme` is on — i.e. **System live-switching on mobile
  already exists and already works**; this task adds VeyraN content, not new
  plumbing.
- Native iOS: no `overrideUserInterfaceStyle`/appearance lock was found in the
  audit; the OS-level appearance is left to follow the device setting and the
  JS-side `Appearance` API, consistent with the above.
- **Prior VeyraN visual work already in this branch**
  (`apps/mobile/app/utils/apple-visual-tokens.ts`) is a presentation-only
  layer of iOS/iPad-specific radii/spacing/shadow constants that explicitly
  *reads its colors back out of* `VariantsWithStaticColors` (i.e. out of
  whatever `@notesnook/theme` theme is active) rather than hardcoding its own
  palette. It is layered **on top of** the engine, not a competing source of
  truth, so it needs no changes for VeyraN Light/Dark to flow through it
  automatically once the active theme's colors change.
- Similarly, `apps/web/src/styles/veyran-mac-*.css` (Electron/macOS shell
  chrome) key off `html[data-theme="light"|"dark"]` (set by
  `theme-provider/index.tsx` from `theme.colorScheme`) and reference
  `var(--accent)` from the engine's emitted CSS — also downstream of the
  engine, not touched by this change.

## 3. Migration design actually implemented

Single rule, applied independently on web/desktop and mobile, keyed on the
bundled default theme's **id**, never on `colorScheme` alone:

> If (and only if) the user's persisted light theme has `id === "default-light"`
> **and** their persisted dark theme has `id === "default-dark"`, replace both
> with `ThemeVeyranLight`/`ThemeVeyranDark` (`@notesnook/theme`). Their
> `colorScheme` / `followSystemTheme` / `useSystemTheme` preference is left
> exactly as-is. Any other theme id (a marketplace theme, a hand-edited
> custom theme, or a theme the user re-selected that happens to already be
> VeyraN) is left completely untouched.

New installs get `ThemeVeyranLight`/`ThemeVeyranDark` as their light/dark
theme from the very first run, with System appearance already the default
(mobile) or set explicitly true (web/desktop first-run only, guarded so an
existing install's `followSystemTheme: false` is never overwritten).

**Implementation notes (web/desktop, `apps/web/src/stores/theme-store.ts`):**
the migration check lives inside the module's `getTheme()` helper itself
(not just the class field initializers), because `setColorScheme()` --
the same function the live System-appearance effect in
`theme-provider/index.tsx` calls when the OS scheme flips -- also calls
`getTheme()` directly. An earlier draft only migrated the field
initializers, which meant a user still on the old default who switched
scheme (manually, or via a live OS change while following system) would
have briefly seen the old Notesnook theme again instead of VeyraN; this was
caught by writing `apps/web/__tests__/veyran-theme-migration.test.ts` and
fixed before considering this correct. The pre-hydration flash-avoidance
script in `apps/web/src/index.ts` duplicates the same id check for the same
reason (it runs before the store exists at all).

**Implementation notes (mobile):** the migration predicate is factored into
a small, dependency-free module,
`apps/mobile/app/utils/veyran-theme-migration.ts` (no `react-native`, no
MMKV, no stores), shared between `services/settings.ts`'s version-gated
`migrateSettings()` step (`settingsVersion` 1 → 2) and the iOS share
extension's theme fallback in `share/store.ts`. Extracting it this way
means it can be unit-tested directly without mocking the share extension's
or the settings service's full dependency graph, following the same
"mock the whole heavy module away" convention the existing mobile test
suite already uses for `services/settings.ts` (see
`services/reminder-widget-completion.test.ts`, which mocks `./settings`
wholesale rather than importing it).

## 5. Contrast/restraint validation

`packages/theme/scripts/validate-veyran.mjs` is a dependency-free Node script
(no monorepo install required — see §6 on tooling limits) that:
- Re-checks the `ThemeDefinition` schema's structural + hex-pattern rules
  (mirrors `validator.ts` without importing it, since nothing in this repo
  checkout has `node_modules` installed — see §6).
- Computes real WCAG 2.1 contrast ratios (relative luminance, alpha-composited
  onto the theme's own root background) for every scope's resolved
  paragraph/heading/icon/placeholder/accent-on-background, secondary-surface
  text, selected-row text and selected-vs-unselected surface separation,
  hairline border/separator visibility, and error/success state text —
  4.5:1 for body text, 3:1 for large text/icons/non-text, 1.2:1 minimum
  surface-separation for selection state.
- Checks the base accent's HSV saturation stays ≤0.75 (restrained accent,
  no neon fill).

Run: `node packages/theme/scripts/validate-veyran.mjs [--verbose]`.
Current result: **310/310 assertions pass** for both `veyran-light` and
`veyran-dark`.

(Note: an earlier version of this script had a real bug — `over()` assumed
both arguments were hex strings, but `contrast()` passes it an
already-composited `{r,g,b,a}` object for the second argument — fixed in this
session before trusting any of its output.)

## 7. Focused tests added this session

- `apps/web/__tests__/veyran-theme-migration.test.ts` (vitest + happy-dom,
  matches this directory's existing convention): unit-tests the pure
  `migrateLegacyDefaultTheme()` helper, then re-imports `theme-store.ts`
  fresh (via `vi.resetModules()`) against four seeded `localStorage` states
  to cover (a) a brand-new install defaulting to System appearance +
  VeyraN, (b) a user still on the shipped default theme migrating while
  their explicit `colorScheme`/`followSystemTheme` stay untouched, (c) an
  explicit/custom theme never being touched even when the *other* scheme
  slot is still on the shipped default, and (d) a live System-appearance
  scheme change (simulating what `BaseThemeProvider`'s effect does)
  correctly landing on VeyraN Dark rather than the old default. The
  `themes-router` marketplace-update call is mocked out so the tests never
  touch the network.
- `apps/mobile/app/utils/veyran-theme-migration.test.ts`: unit-tests the
  shared, dependency-free migration helper directly (no react-native mocking
  needed), covering the same "migrate old default / preserve explicit or
  custom / independent light+dark slots" cases as above.

  monorepo root** (`npm ping` succeeds, so the registry is reachable, but

  booted (`iPhone 18 Pro`, `iPad Pro 13-inch (M5)`, plus others shutdown) via
  `xcrun simctl list devices available`, but this session did not build or
  launch the app on any of them, and did not open the web/desktop app in a
  browser or Electron shell. Any visual/contrast claim in this document is
  from the numeric WCAG validator above, not from a rendered screenshot.
  This should be treated as **presentation-layer code review + numeric
  contrast validation only**, not visual QA.
