# Tasks and reminders architecture

## Domain and persistence

Tasks and Task Lists are independent of Notes and the editor. `packages/core/src/collections/tasks.ts` owns their model, validation, smart queries, recurrence, completion, and migration. Each Task and List has its own stable ID and its own versioned record. The user-facing Reminder schedule is an optional `YYYY-MM-DD` local calendar date and optional `HH:mm` wall time. Date-only reminders notify at 09:00 local time. Priority and flag are distinct fields. Older `dueDate`, `dueTime`, and `reminderAt` fields remain on stored records for older-client compatibility. `taskReminderSchedule()` projects their meaning at read time; new writes use `scheduleVersion: 2` and the unified fields, without bulk rewriting synced records.

The sync server currently accepts a fixed set of Notesnook item types. Fork Task records therefore travel as namespaced `settingitem` records, one item per Task or List. The record's `value` is a JSON string with `schemaVersion: 1`; its carrier ID is deterministic from the namespaced key. The Task facade validates and reads these records without changing the fixed-key user Settings API. Normal Notes, Notebooks, attachments, and their ciphertext formats are unchanged. `settingitem` already participates in the standard E2EE sync collector and backup export/import. The local SQL database remains encrypted through its existing key path. The Task schema version is independent of the Notesnook wire database version.

The official Web App does not interpret fork Task settings. Its normal data and login remain on the existing protocol. A newly created Web Reminder can be imported into Tasks by the fork on its next sync. Rich Tasks have no live Reminder projection: two editable representations would create ambiguous authority and overwrite rich fields when Web rewrites a Reminder. This means fork Tasks are invisible in the official Web App. The fork's own desktop renderer uses the Task UI. During staged rollout, older clients still see the retained source Reminder.

## Legacy migration and recovery

The default Task List has a deterministic ID and localized display name. Each legacy Reminder maps to a deterministic Task ID derived from its Reminder ID. Migration writes the Task and retains the original Reminder without changing its enabled state, so older clients continue to alert during a staged rollout. Updated mobile and desktop clients locally exclude converted source Reminders from their Reminder views and alert planners. A retry sees the Task without creating another. Existing Task tombstones block resurrection and keep local source suppression after deletion. Title, description, due timestamp, active snooze timestamp, supported recurrence, and local-only state are mapped; unsupported legacy recurrence modes remain untouched for later handling. For a recurring Reminder whose stored timestamp is stale, migration evaluates the supported RRULE from the original local wall-clock seed and starts the Task at the first scheduled occurrence at or after migration time. It preserves the original series anchor so later completion remains schedule-relative, and a future snooze remains the initial alert. Invalid legacy rows are skipped. Disabled Reminders retain their due date but do not gain an active notification. Migration runs at startup, after sync, and after backup import, with serialized maintenance to prevent concurrent conversion and recurrence passes.

## Recurrence and completion

RRULE values use RFC 5545 syntax via the `rrule` library. The series start and each scheduled occurrence are retained. Completing an occurrence marks that Task completed and writes the next occurrence under a deterministic ID derived from the series and next scheduled date/time. Restart reconciliation fills a missing next occurrence after a crash. The original series anchor survives due-date edits. The next date is calculated from the schedule, with late completion skipping missed dates instead of drifting by completion time; persisted completion wall date/time keeps that choice stable across timezones. Completed occurrences remain in history. Reopening a completed recurring occurrence is rejected while a generated next occurrence or its tombstone exists, avoiding two active occurrences and accidental resurrection after deletion.

## Smart lists and sorting

Today includes incomplete Tasks with a Reminder date today or earlier. Scheduled includes incomplete Tasks with a future Reminder date. All and Flagged include incomplete Tasks; Completed keeps completion history. Ordering is deterministic by Reminder date, time, creation time, and ID. The Task facade reads from the settings cache and computes these views in memory; this should be profiled again if collections grow far beyond several thousand Tasks. Favorites are an independently synced, ordered settingitem collection: the initial five smart views are projected only while the preference record is absent, so an intentional empty list remains empty. Favorites may also include custom Task Lists. Lists have validated SF Symbol and color identifiers with safe defaults for old records.

## Notifications and widget

On iOS and iPadOS, `task-notifications.ts` reconciles stable `task:<id>` Notifee triggers against current Task records, including on foreground return and App Lock setting changes. Recurring series prearm five future occurrences even if the current Task is never completed. The mobile UI warns that reopening the app is required to prepare further occurrences. Edits replace changed triggers; completion and deletion cancel them. Urgent timed Tasks use AlarmKit on iOS 26+ with authorization; an unsupported, denied, or failed native alarm uses a labeled standard notification when notification permission is available, and the Task detail shows the fallback state. The paths are mutually exclusive for each occurrence. Alarm UUIDs derive from account and occurrence identity and carry a fixed app marker so alarms can be found even if the ownership cache is lost. Stopping an AlarmKit alert never completes its Task — it silences the alert and leaves a silent, generic "stopped, still incomplete" Live Activity card (built from a prepublished, non-content alarm identity: Task id, occurrence instant, revision, opaque account scope and the App Lock placeholder). That stopped card and the overdue Lock Screen / expanded-island card carry a round, tappable completion control that runs `TaskAlarmCompleteIntent` through the widget's existing durable completion queue and host bridge (`LiveActivityIntent`, iOS 17+, validated against the approved snapshot for the exact occurrence); it never reports a completion the host did not confirm, and a legacy card with no occurrence identity keeps a static circle and opens the Task instead. The alarm's own Live Activity deliberately has no completion control, because an alarm identity names a presentation rather than the occurrence the person means. Each scheduled alarm is tinted the app's fixed system blue and wires the system Stop control to `TaskAlarmStopIntent` ahead of the Snooze `secondaryIntent`; Snooze postpones by nine minutes. App Lock redacts alarm and notification titles; where AlarmKit cannot update a presentation in place, an already-presenting unredacted alarm is stopped (not left showing a real title) and reported honestly if it cannot be removed. Notification permission is requested from the editor when a user saves a scheduled Task, not at app launch. Permission denial does not prevent Task persistence. A Task notification/widget/link tap goes through one shared resolver (`task-navigation.ts#openTaskInContext`): it does not read the protected Task domain until auth/App Lock/hydration is ready (a cold or locked tap queues a bounded, minimal intent that is consumed once after unlock and cleared on logout/account change), rejects a payload naming a different account before any Task lookup, then re-reads the Task's *current* List and opens it with that row scrolled into view and briefly highlighted — never the editor, never a focused input. A widget "Reschedule" link is a distinct, explicitly parsed action: when the claimed revision still matches the freshly read record it additionally opens the Task's own detail schedule with the date/time picker expanded (a stale revision degrades to a safe List+highlight open), and a link's opaque account-scope token, empty-but-present identity parameters, duplicate parameters, extra path segments and fragments are all rejected. Warm and cold-start taps both use it, and the last accepted rapid tap wins. Separately, an incomplete **Urgent** Task whose timed reminder has already fired may own a silent overdue Live Activity (Lock Screen / Dynamic Island, public ActivityKit, iOS 16.2+), capped at five and reconciled from the app on the same cadence as alarms and notifications; switching Urgent off (or completing, deleting, removing the reminder from, or rescheduling the Task) clears it. It belongs to the Urgent alarm feature — an ordinary reminder never owns one — it never makes a sound, and the AlarmKit Stop intent now attempts to start the silent card directly in the app process. A system refusal leaves a durable pending Stop for a later authorized reconciliation; it is not a guaranteed background launch. See `docs/urgent-reminders-architecture.md` for the full mechanism and its limits. The existing legacy Reminder scheduler is kept only for records not yet converted on the local updated client; older clients continue scheduling the retained source.

The iOS WidgetKit extension reads a narrow, versioned Today snapshot from the App Group. Schema v3 retains the `dueDate` and `dueTime` wire key names for its Swift decoder, but their values come from the unified Reminder schedule. It includes only IDs, shortened and sanitized titles, schedule display fields, priority, flag, appearance, and a generation date/timezone/UTC offset; no keys, tokens, Note contents, or full database. The snapshot is atomically written with first-unlock file protection and excluded from device backups. App Lock replaces it with a redacted privacy snapshot containing no Task IDs or titles; the widget displays a private placeholder until App Lock is disabled. Account changes and logout clear it through the same serialized write queue. Swift derives overdue styling at render time and schedules timeline entries for due times and midnight. It rejects a snapshot from another local day or timezone/UTC offset and asks the user to open Notesnook to refresh; a new day's Tasks cannot appear while the app remains closed. Widget and Live Activity completion reuse the existing App Group action queue and app-process completion host on supported OS versions. The native snapshot validates scope and revision (the Live Activity also validates its due instant), and the host checks current account, App Lock, database readiness and Core revision before `completeIfUnchanged`. Enqueuing alone is not success. Unsupported or unavailable execution leaves an app/open/unlock path; no extension directly modifies the encrypted store. The app refreshes the snapshot and reconciles alarm/notification/Activity surfaces after a confirmed write. Thus the extension never writes the encrypted store or the Notes editor. The small, medium, and large layouts use a readable single column.

On macOS, the Electron renderer sends a full reminder schedule to the main process, which owns in-memory timers keyed by stable Task ID. These continue while the macOS app remains running after its last window closes; notification clicks restore the window and route to the Task. Desktop and browser Task alerts use a generic localized title when App Lock is configured, and an App Lock state change replaces previously sent desktop titles with generic titles. Starting a renderer while already locked clears any previously armed main-process schedule before the normal refresh. The current Electron process does not provide a system-level notification schedule after the application quits; this is a known limitation requiring a native background delivery path if quit-app delivery becomes a release requirement.

## Backup, sync, and compatibility limits

Task and List carrier records are exported and imported by existing backup code. Tombstones follow the normal sync path. The fork does not add an unsupported server item type or bump the shared wire database version. Official Web clients may retain unknown Task carrier settings but do not present them. Importing a fork backup containing local-only Tasks into an older official Web App deserves special caution: that app does not have the fork's `localOnly` carrier column, so local-only intent may not survive its subsequent sync, although its server traffic remains encrypted.

Task edits use the existing per-record last-write-wins sync behavior. Concurrent edits to different Tasks are independent. Concurrent offline edits to the *same* Task, Favorites order, or List appearance can still overwrite one another, matching generic Notesnook item merge behavior rather than field-level conflict resolution. This is a known limitation. Older clients continue to alert on the retained source Reminder during rollout, including after the converted Task is completed on a newer client; preserving alert delivery takes priority over silently disabling Reminders on older clients. The import is a one-way cutover: edits to the retained source on an older client do not flow into the Task. The Task editor presents this warning for imported Tasks.

## Platform boundaries

iPhone and iPad use dedicated React Native Task screens. macOS uses the existing Electron and web renderer architecture. None of the Task domain code references TipTap, editor content, Note IDs, or Note links. Presentation navigation can open Task screens without changing editor internals.

Legacy editor actions that formerly opened the Reminder editor now open standalone Task detail. The supplied Note reference is intentionally ignored because Tasks do not have Note relationships. Non-editor Note properties and row badges for the old relation were removed from the Apple-facing UI.

## Validation

Core domain tests cover CRUD, lists, smart queries, date-only behavior, recurrence rules, DST cases, migration retry and interruption, tombstones, collector behavior, and backup round trips. Mobile widget and notification planner tests cover snapshots, deep links, stable IDs, rescheduling, cancellation, App Lock privacy, and intent expiry. Both iPhone and iPad have ARM64 simulator builds and earlier Detox Task create/complete/Completed smoke coverage. The redesigned iPhone UI was also exercised manually on a signed simulator build: an Urgent recurring Task, native AlarmKit authorization, List appearance, default-List Favorites persistence across restart, and Note content save/reopen with the editor visible. The rebuilt iPad app showed the two-pane Tasks layout and saved a dated, timed Task that appeared in Scheduled. Desktop Playwright covers Task create/complete/reopen and launch; scheduler Vitest covers in-process delivery. Exact results and remaining runtime limits are recorded in `NOTESNOOK_APPLE_HANDOFF.md`. The 2026-10-08 Urgent parity change adds native Stop handling, occurrence-scoped lifecycle markers, a calm timer-free reminder Live Activity, background completion through the existing encrypted Task host, and explicit reschedule links. Current build/test evidence and conditional iOS behavior are recorded in `artifacts/urgent-reminders-qa.md` and `artifacts/urgent-reminders-parity-report.md`; historical test counts above are not the current parity acceptance gate.
