# Tasks and reminders architecture

## Domain and persistence

Tasks and Task Lists are independent of Notes and the editor. `packages/core/src/collections/tasks.ts` owns their model, validation, smart queries, recurrence, completion, and migration. Each Task and List has its own stable ID and its own versioned record. Task due dates are `YYYY-MM-DD` calendar dates; optional due times are local `HH:mm` wall times. Reminder times are separate epoch timestamps. Priority and flag are distinct fields.

The sync server currently accepts a fixed set of Notesnook item types. Fork Task records therefore travel as namespaced `settingitem` records, one item per Task or List. The record's `value` is a JSON string with `schemaVersion: 1`; its carrier ID is deterministic from the namespaced key. The Task facade validates and reads these records without changing the fixed-key user Settings API. Normal Notes, Notebooks, attachments, and their ciphertext formats are unchanged. `settingitem` already participates in the standard E2EE sync collector and backup export/import. The local SQL database remains encrypted through its existing key path. The Task schema version is independent of the Notesnook wire database version.

The official Web App does not interpret fork Task settings. Its normal data and login remain on the existing protocol. A newly created Web Reminder can be imported into Tasks by the fork on its next sync. Rich Tasks have no live Reminder projection: two editable representations would create ambiguous authority and overwrite rich fields when Web rewrites a Reminder. This means fork Tasks are invisible in the official Web App. The fork's own desktop renderer uses the Task UI.

## Legacy migration and recovery

The default Task List has a deterministic ID and localized display name. Each legacy Reminder maps to a deterministic Task ID derived from its Reminder ID. Migration writes the Task first, then retains and disables the original Reminder. This preserves its full payload for rollback or Web inspection while preventing duplicate alerts. A retry sees the Task and finishes the disable step without creating another Task. Existing Task tombstones block resurrection from an old Reminder. Title, description, due timestamp, active snooze timestamp, supported recurrence, and local-only state are mapped; unsupported legacy recurrence modes remain untouched for later handling. Invalid legacy rows are skipped. Disabled Reminders retain their due date but do not gain an active notification. Migration runs at startup, after sync, and after backup import, with serialized maintenance to prevent concurrent conversion and recurrence passes.

## Recurrence and completion

RRULE values use RFC 5545 syntax via the `rrule` library. The series start and each scheduled occurrence are retained. Completing an occurrence marks that Task completed and writes the next occurrence under a deterministic ID derived from the series and next scheduled date/time. Restart reconciliation fills a missing next occurrence after a crash. The original series anchor survives due-date edits. The next date is calculated from the schedule, with late completion skipping missed dates instead of drifting by completion time; persisted completion wall date/time keeps that choice stable across timezones. Completed occurrences remain in history. Reopening a completed recurring occurrence is rejected while a generated next occurrence or its tombstone exists, avoiding two active occurrences and accidental resurrection after deletion.

## Smart lists and sorting

Today includes incomplete Tasks due today, overdue Tasks, and Tasks with a reminder today. Scheduled includes incomplete Tasks with a future due date or reminder. All and Flagged include incomplete Tasks; Completed keeps completion history. Ordering is deterministic by due date, due time, creation time, and ID. The Task facade reads from the settings cache and computes these views in memory; this should be profiled again if collections grow far beyond several thousand Tasks.

## Notifications and widget

On iOS and iPadOS, `task-notifications.ts` reconciles stable `task:<id>` Notifee triggers against current Task records, including on foreground return and App Lock setting changes. Edits replace changed triggers; completion and deletion cancel them. Notification data contains only the Task ID, revision, and privacy state for routing. With App Lock enabled, alert titles are generic. Permission denial does not prevent Task persistence. A Task tap routes to Task detail; cold-start taps are handled after database initialization. The existing legacy Reminder scheduler is kept only for records not yet converted.

The iOS WidgetKit extension reads a narrow, versioned Today snapshot from the App Group. Schema v3 includes only IDs, titles, due display fields, priority, flag, appearance, and a generation date/timezone/UTC offset; no keys, tokens, Note contents, or full database. The snapshot is atomically written with first-unlock file protection and excluded from device backups. App Lock replaces it with a redacted privacy snapshot containing no Task IDs or titles; the widget displays a private placeholder until App Lock is disabled. Account changes and logout clear it through the same serialized write queue. Swift derives overdue styling at render time and schedules timeline entries for due times and midnight. It rejects a snapshot from another local day or timezone/UTC offset and asks the user to open Notesnook to refresh; a new day's Tasks cannot appear while the app remains closed. Widget completion opens the main app through a Task-specific deep link. The app validates the ID and durably queues only the Task ID, account ID, and enqueue time in local MMKV before attempting completion. It replays after the database is ready and App Lock is clear, drops pending actions older than 24 hours, acknowledges only after the idempotent domain operation succeeds, and clears the queue on logout or account change. A crash between domain write and acknowledgement safely retries the same stable Task ID. The app then refreshes the snapshot. Thus the extension never writes the encrypted store or the Notes editor. The small, medium, and large layouts use a readable single column.

On macOS, the Electron renderer sends a full reminder schedule to the main process, which owns in-memory timers keyed by stable Task ID. These continue while the macOS app remains running after its last window closes; notification clicks restore the window and route to the Task. The current Electron process does not provide a system-level notification schedule after the application quits; this is a known limitation requiring a native background delivery path if quit-app delivery becomes a release requirement.

## Backup, sync, and compatibility limits

Task and List carrier records are exported and imported by existing backup code. Tombstones follow the normal sync path. The fork does not add an unsupported server item type or bump the shared wire database version. Official Web clients may retain unknown Task carrier settings but do not present them. Importing a fork backup containing local-only Tasks into an older official Web App deserves special caution: that app does not have the fork's `localOnly` carrier column, so local-only intent may not survive its subsequent sync, although its server traffic remains encrypted.

Task edits use the existing per-record last-write-wins sync behavior. Concurrent edits to different Tasks are independent. Concurrent offline edits to the *same* Task can still overwrite one another, matching generic Notesnook item merge behavior rather than field-level conflict resolution. This is a known limitation.

## Platform boundaries

iPhone and iPad use dedicated React Native Task screens. macOS uses the existing Electron and web renderer architecture. None of the Task domain code references TipTap, editor content, Note IDs, or Note links. Presentation navigation can open Task screens without changing editor internals.

Legacy editor actions that formerly opened the Reminder editor now open standalone Task detail. The supplied Note reference is intentionally ignored because Tasks do not have Note relationships. Non-editor Note properties and row badges for the old relation were removed from the Apple-facing UI.

## Validation

Core domain tests cover CRUD, lists, smart queries, date-only behavior, recurrence rules, DST cases, migration retry and interruption, tombstones, collector behavior, and backup round trips. Mobile widget and notification planner tests cover snapshots, deep links, stable IDs, rescheduling, cancellation, App Lock privacy, and intent expiry. Both iPhone and iPad have ARM64 simulator builds and Detox Task create/complete/Completed smoke coverage. An iPhone Detox test opens a New Note, saves content, leaves, and reopens it, guarding against the prior black-editor regression. Desktop Playwright covers Task create/complete/reopen and launch; scheduler Vitest covers in-process delivery. Exact results and remaining runtime limits are recorded in `NOTESNOOK_APPLE_HANDOFF.md`.
