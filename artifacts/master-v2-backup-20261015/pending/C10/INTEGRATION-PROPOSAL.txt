WHY THE OBVIOUS SMALL PATCHES DO NOT MEET C10
A. Remove `rootRoute === "FluidPanelsView"` from sidebarOwnsPrimary, or whitelist Tasks/Search without mounting a visible replacement: no sidebar appears on those screens, but the fallback disappears. Sole-return-path regression.
B. Wrap Tasks and Search each in a new or broadened Mac sidebar wrapper: visually plausible but produces per-route sidebars in addition to Notes' sidebar. Local source filter/expanded/scroll ownership is no longer a single retained instance, and narrow/fullscreen transitions need independent ownership resolution. Cache-by-screen type does not solve shared instance/state continuity.
C. Leave FluidPanelsView mounted underneath an opaque covering route: an offscreen retained child is not a visible reachable sidebar. Transparent overlays/partial presentation would need a wider native navigation, input/hit-testing and focus contract; do not improvise a transparent card as a navigation fix.
D. Render actual Tasks/Search as local conditional children inside the Notes sidebar owner: that changes root focus/route semantics and screen lifecycle. Existing selectAppleSection, onStateChange, task details, Search result open and compose-return routes would need coherent integration, not a new route alias or store. C10 cannot responsibly claim that from the current adapter tests.

SMALLEST COHERENT DIRECTION FOR ARCHITECTURE REVIEW
Review a single retained iPad source-pane owner above the Notes/Tasks/Search content transition. Preserve existing route names/keys, section handler and data stores. The source pane owns C4 controls and sidebar local state once; the root-route content outlet changes beside it. On wide eligible sections, exactly one owner is visible and the strip/offset switch atomically. On narrow<700, medium, fullscreen, non-iPad/Mac, intro/loading, or a covering route without that visible host, the existing fallback remains authoritative.

This is a design direction, not a proposed runnable patch. Before authoring, Root's independent `deepseek_review(kind="architecture")` must decide:
- Can the existing real FluidPanelsView split host expose/reuse its sidebar once without moving or rekeying its AppNavigationStack/editor, or must the pane owner move above RootStack? The real host must be explicitly included in the next review/ownership scope; C10 did not inspect it beyond documented host references in the permitted seams.
- How will exactly one host retain source local filter/scroll/expanded state across Notes/Tasks/Search and across wide->medium/narrow->wide, while maintaining the drawer/pager provider and focus/navigation context? Keeping a store is not equivalent to retaining a component instance.
- Which measured dimension represents the real window, and which is the section's available content width? Keep root mode decisions based on actual root width; do not overwrite that shared measurement when adding a sidebar. Audit Tasks' overview/list split under the remaining measure.
- How are section route identity, task-detail/settings overlays, Search->note, note compose/fullscreen return and route focus synchronized with an always-mounted source pane? Only suppress the strip for routes the visible host actually covers. Do not blanket-whitelist TaskDetail/Settings or hide their return path.
- Can those changes fit the3production/2existing-test budget without changing Mac/iPhone? If not, obtain a separate bounded Root-owned host packet instead of adding ad hoc wrappers to stay nominally under a file count.
